# 요구사항 및 범위 (Draft v0.1)

## 1. 목표와 비목표
**목표:** 대학 수강신청 오픈 시각에 집중되는 트래픽을 안정적으로 수용하는 인프라를 설계하고, 2단계 대기열 도입의 효과/트레이드오프를 실측합니다. 실제 운영 문제(확장 지연, DB 경쟁, Task/Redis 장애, 복구)를 재현하고 대응 절차를 남깁니다.

**비목표:** 대학 학사 업무 전반 구현, 상용 대학 SSO 연동, 완전한 분산 트랜잭션 플랫폼, 멀티 리전 Active-Active.

## 3. 비기능 요구사항
- **정합성:** 수강신청 확정 건수는 강의 정원을 넘지 않음. 학생·강의 조합당 활성 신청은 최대 1건.
- **공정성:** 1차는 서버가 확정한 입장 순서 기준. 2차는 접수 순서와 처리 순서를 명시하고, 동일 강의의 뒤 요청이 앞 요청을 부당하게 앞서지 않도록 설계·검증. 전역적인 엄밀 FIFO 보장은 초기 목표가 아님.
- **보안:** 서버에서 JWT 인증, 입장권/신청권 검증. 클라이언트 순번·시각·상태를 신뢰하지 않음. 비밀번호 해시, 비밀정보 환경별 분리.
- **내결함성:** Redis 불가 시 신규 입장/신청을 기본 거부(fail closed)하고 우회 요청으로 정원을 침해하지 않음. DB가 최종 정합성을 보장.
- **새로고침/이탈:** 브라우저 unload 알림은 전달 보장되지 않으므로 1차 대기권에는 짧은 lease와 갱신을 사용. 이전 대기권을 재사용해 순번을 복원하지 않으며 재입장 시 원자적으로 이전 대기권 무효화 후 맨 뒤에 배치. 2차 신청의 이미 처리 중/확정된 변경은 새로고침으로 롤백되지 않음.
- **관측:** 요청별 requestId, queueTicketId, enrollmentRequestId를 사용해 로그와 결과를 연계(민감정보 제외).
- **재현성:** 로컬 Docker Compose와 AWS 배포의 애플리케이션 동작을 일치시키고, IaC로 환경 재생성 가능하게 목표.
- **성능:** 목표 RPS/동시 인원/SLO는 **초기 부하 테스트 후 결정**. 강제 숫자를 성능 성과로 표기하지 않음.
- **비용:** 테스트 환경으로 제한, AWS 예산 알람 및 종료/삭제 절차 마련.

## 4. 비교 실험 설계
- 동일 테스트 데이터 및 부하 패턴(예: 오픈 직후 동시 로그인·입장·강의 조회·특정 강의 집중 신청).
- 모드 A: 1차·2차 대기열 OFF → 인증 뒤 직접 조회·동기 신청. DB 정합성 유지.
- 모드 B: 1차·2차 대기열 ON → 입장 허가/신청 비동기 처리.
- 추가 세부 실험은 1차만 ON / 2차만 ON, ECS Task 확장 전후, 사전 증설 vs 자동 증설.
- 비교 시 **서버 에러율뿐 아니라 접수부터 최종 결과까지 사용자 체감 대기시간**, 전체 완료 건수, 큐 적체, DB 부하, 비용을 동등하게 기록.
- 한정 정원으로 접수 후 대다수가 즉시 마감되는 상황 외에, 충분한 정원·다수 강의 요청의 지속 쓰기 부하 시나리오도 사용.

## 5. 3주 단계 계획
1. **MVP:** 인증, 강의/신청/취소, DB 동시성 보장, 로컬 Docker.
2. **대기열:** 입장권/접수 토큰/처리 결과, Redis 장애·재시도 검증.
3. **AWS:** VPC, Fargate, RDS, ElastiCache, ALB, S3/CloudFront, IaC.
4. **운영:** CloudWatch/Grafana/k6, Auto Scaling, 장애·백업 복원.
5. **증빙:** Grafana 스크린샷, 실험 데이터, 결정 근거, Runbook/Playbook/Postmortem.

## 6. 확정 필요 (구현 전)
- 시작 전 입장 버튼 클릭 허용 여부: 기본안은 **정각 이후 대기열 등록 가능**. 실제 대학 UI 경험과 다른 정책이 필요하면 수정.
- 신청 요청의 공정성 정의: 강의별 FIFO 수준의 엄격성 및 처리자 병렬성.
- 입장권의 활성 세션 상한, TTL·갱신 방식, 큐/worker 처리율: 부하 테스트에 따라 조정.
- 로그인과 입장 API 분리 시 WAF/rate-limit 정책.
