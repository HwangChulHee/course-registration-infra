## 실행 범위와 판정

- 수정 후 정식 smoke 3회: A 2 RPS, B 2 RPS, C 10명/1석. 전부 통과.
- 본 실험 **82회**: 27개 비교 구성 각 3회(81회) + 원래 E 고부하의 중단 1회. 결과는 **PASS 63 / LIMITED 18 / FAIL 1**.
- A→B→C1~C5→D 순서로 baseline을 각 3회 실행했습니다. E에서 처음 0.5 CPU의 100 RPS 읽기가 보호 중단되어 나머지 원래 고부하를 미실행 처리하고, **A 10 RPS / B 5 RPS / D 100명** 공통 스케줄을 0.5/1/2 CPU에서 각 3회 비교했습니다. baseline은 앞서 실행한 같은 설정을 재사용했습니다.
- **모든 85회(smoke 포함)의 SQL 인원·정원·중복 검사 통과**. 본 실험의 서버 5xx 0, 관측된 네트워크 실패/timeout 0. 다만 중단 1회에는 **드롭 55 및 응답 미완료 요청 200**이 있으며, 이를 성공/5xx/timeout 어느 쪽으로도 임의 분류하지 않았습니다.

- 백엔드 실제 PostgreSQL 회귀 테스트 **12개**, 하네스 단위 테스트 **5개** 통과. 기존 React UI·신청 도메인 규칙은 변경하지 않았습니다. 계측 API만 `local & benchmark` 프로필에 추가했습니다.

### 경합 병목의 근거

- C2 첫 반복의 course-row-lock SQL 1,000회 누적 실행시간은 약 **1,986ms**, C3 첫 반복은 약 **2,611ms**였습니다. B-100 첫 반복에서는 같은 lock SQL 600회가 약 **11.15ms**였습니다. 단일 강의 행을 잠그는 구간에서 대기 시간이 늘어난다는 가설을 지지합니다. 이 누적 실행시간은 여러 요청의 합계이며 wall duration이나 DB CPU 시간과 동일하지 않습니다.
- C2 첫 반복의 Hikari acquire 누적 시간 증가 약 **5.41초 / 2,051회**, C3 첫 반복 약 **7.06초 / 2,052회**. 비교적 큰 burst가 pool/락 대기를 유발한 근거입니다. warm-up/collector의 borrow도 일부 포함됩니다.
- C2에서는 실제 lock wait 3개가 샘플에 잡혔습니다. 다른 1초 실행에서 관측 0이라고 경합이 없다고 결론내리지 않습니다. 1초 사례의 측정 구간 표본은 대개 1개로 peak를 놓칠 수 있습니다.
- C4 분산은 같은 총인구·좌석 수에서 p95가 낮아졌습니다. 반면 C5는 강의 수뿐 아니라 도착률도 C2보다 낮으므로, C5의 개선을 강의 분산 효과 하나로 단정할 수 없습니다.

## E: CPU/메모리 비교와 안전 중단

원래 비교 일정 A-100/B-50/D-500 중 첫 **0.5 CPU/1GiB A-100**은 100/s × 6초 목표를 달성하지 못했습니다.

- 목표 600회, 실제 시작 319회, 응답 완료 119회, **드롭 55**, 중단 당시 **응답 미완료 200**.
- 마지막 측정 event 약 3.66초, 응답 수/목표 6초로 정규화한 값 **19.83/s**. 실제 마지막 event까지의 완료율은 실행 JSON의 별도 필드로 제공하며, 미완료 요청이 있어 이를 정상 지속 처리량으로 해석하지 않습니다.
- 응답 완료분 p50/p95/p99 약 **1,010 / 2,073 / 2,573ms**. 종료 코드 99와 k6 dropped threshold 메시지로 보호 중단을 확인했습니다.
- 서버 5xx/관측 network failure 0, OOM 0. backend CPU quota throttling이 크게 증가했고 Hikari active/pending peak 7/1을 관측했습니다. cgroup v1의 누적 throttled time은 병렬 스케줄 구간을 포함할 수 있어 wall time이나 CPU 사용률로 환산하지 않았습니다.
- 이때 사용 heap은 약 36MiB이고 Docker VM 가용 메모리 약 12.5GiB로 메모리 고갈 근거는 없습니다. **CPU quota와 기동 직후 JIT/실행 상태가 주요 후보**입니다. 2초 warm-up 뒤의 짧은 cold-ish 실행이므로 '0.5 CPU는 항상 100 RPS 불가능'이라는 고정 용량 결론은 내리지 않습니다.

그 후 무리한 같은 고부하 반복을 중지하고 동일한 저부하 스케줄로 비교했습니다. 각 셀은 3회 p95 중앙값입니다.

## 계측의 한계와 후속 개선 후보

1. **발생기/공유 VM의 타이밍을 먼저 안정화**: 18회 시간창 미달은 저부하에서도 발생했고 수 초의 도착 공백이 있었지만 HTTP latency는 수 ms인 경우가 많았습니다. 서버 처리 지연과 별개인 발생기/WSL 시간·스케줄 조건 후보입니다. 현재 자료만으로 VM clock, CPU scheduling, 외부 부하 중 어느 하나를 확정하지 않습니다. 다음에는 별도 발생기, 고정 VM 리소스·background 통제, 단조/벽시계 비교 및 반복 순서 무작위화를 적용합니다.
2. **warm-up과 steady window 분리**: 현재 A/B 각 6초, D 5초, 3회 반복은 최대 용량/장기 안정성/통계적 신뢰구간을 정하기에 부족합니다. 30초 이상 고정 warm-up, 60초 이상 관측으로 cold/steady를 따로 측정하고, 0.5 CPU의 25→50→100 RPS를 다시 단계적으로 비교하는 것이 우선입니다.
3. **단일 강의의 FULL 경로/잠금 비교**: 현재 FULL 요청도 강의 FOR UPDATE와 중복 확인을 거칩니다. 조건부 UPDATE 방식과 비교하되 duplicate 우선 응답·취소·정원·실패 롤백의 기존 보장을 유지해야 합니다. 측정 없이 Redis queue를 해결책으로 선택하지 않습니다.
4. **pool/JVM 튜닝을 독립 변수로 분리**: Hikari 12는 그대로 유지했습니다. lock 대기가 생긴 상태에서 pool만 늘리면 대기만 옮길 수 있으므로 acquisition/DB lock을 함께 관측해야 합니다. 고정 heap에서 CPU만, 고정 CPU에서 heap만 바꿔야 원인 구분이 됩니다.
5. **메모리·GC·IO 해상도**: 본 실험 sampled heap 최대 약 **93.3MiB**, backend cgroup 약 **377.0MiB**, DB 약 **94.1MiB**, k6 약 **292.8MiB**, VM 가용 메모리 최소 약 **12.08GiB**였습니다. 표본 수는 측정 구간당 1~13개, 평균 간격은 실행별 약 0.77~1.98초이며 collector 오류는 0입니다. 이는 절대 peak가 아닙니다. 더 큰 데이터/긴 실행에서 memory·GC·IO를 다시 봐야 합니다.
6. **통계의 단위와 범위**: PostgreSQL transaction 누적값은 비동기 publication 및 collector/warm-up의 영향을 받습니다. FULL/DUP로 인한 정상 rollback을 500 오류로 세지 않습니다. Hikari acquire MAX는 이전 실행도 포함할 수 있는 rolling 값이며, COUNT/TOTAL_TIME delta와 raw 시계열을 함께 봅니다. DB row count가 commit의 근거입니다.

이번 결과는 동일 로컬 애플리케이션의 실행 증거이며 Fargate vCPU, RDS 사양, 클라우드 비용으로 직접 환산하지 않습니다. AWS/Redis 자원이나 장기 모니터링 시스템은 생성하지 않았습니다.

## 하네스 검증 및 종료

개발 중 k6 종료 경계의 추가 iteration, cgroup v1 경로 차이, setup이 포함된 시간 offset을 수정한 뒤 최종 smoke를 다시 실행했습니다. 해당 진단 실행은 `.bench-results/development-index*.jsonl`에 별도 보관하며 성능 표와 혼합하지 않았습니다. 최종 계측 본 실험은 위 82회입니다.

실험 종료 후에는 startup 이전에도 기존 benchmark 명칭의 volume label을 검사해 다른 프로젝트의 volume을 만났을 때 기동 전에 거부하는 방어 검사를 보강했습니다. 이 사전 검사와 하네스 테스트만 추가했으며 측정된 API/k6 스케줄·DB 초기 상태·리소스 프로필을 바꾸지 않았습니다. 측정 당시의 하네스 지문과 앱 image ID는 실행별 metadata/JSON에 보존합니다.

벤치마크 컨테이너만 `python3 load-tests/bench.py down`으로 정리하고, 전용 결과/volume은 보존합니다. 기존 데모는 계속 실행되며 마지막 SQL 지문도 원본과 동일합니다.
