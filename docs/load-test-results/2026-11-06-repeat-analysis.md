# A–E 추가 전체 2회 반복: 재현성과 편차 분석

**애플리케이션 기능을 변경하지 않고 전체 순서를 2회 추가 실행했습니다.** [실행별 결과와 통계](2026-11-06-repeat-results.md), [정제 JSON](2026-11-06-repeat-runs.json), [원본 분석](2026-11-06-analysis.md)을 함께 참고하세요. 원본 결과 파일은 그대로 보존했습니다.

## 실행 범위·동일 조건 확인

- 추가 본 실험 **56회 = 28개 구성 × 2라운드**, 사전 smoke 3회. 각 라운드 A→B→C1~C5→D→E 순서를 유지했습니다.
- E는 기존 실제 실행을 반복했습니다: 새 half 백엔드에서 A-100 재현 확인 1회, 이후 half/one/two의 A-10/B-5/D-100 공통 저부하. 원래 실행하지 않았던 E 고부하 B-50/D-500과 one/two A-100은 새 성과로 섞지 않았습니다.
- 56회 판정은 **PASS 45 / LIMITED 9 / 보호 중단 FAIL 2**. 실패 2회는 모두 half/A-100에서 기존 k6 드롭 기준으로 중단된 경우입니다.
- 기존 82회와 합하면 본 실험 **138회**입니다. 일반 비교 구성은 이전 3회+추가 2회로 **각 n=5**이며 half/A-100은 이전 1회+추가 2회로 **n=3**입니다.
- 실제 앱/nginx/PostgreSQL image ID가 이전과 일치합니다. `bench.py`, k6 script, Compose 및 리소스 override 원문을 커밋 `7cbcc0b`와 비교했습니다. 요청률·기간·인구·VU·정원·warm-up/cool-down과 실제 Docker/JVM 설정도 실행별로 대조했습니다.
- 전용 DB의 논리 초기 데이터 fingerprint가 이전과 같으며 원래의 사용자/token fixture를 재사용했습니다. warm-up은 기존 20회 읽기/약 2초를 유지했습니다. 고부하 VU/도착률 상한과 오류·드롭·메모리/IO 중단 기준도 변경하지 않았습니다.
- Docker VM은 이전과 같은 20 CPU / 16,647,561,216 bytes 메모리, DB/k6는 각각 2 CPU/2GiB입니다. 데모는 그대로 실행했습니다.
- **추가 59회(smoke 포함) 모두 SQL 정원·인원·중복 검사 통과**. 기존 데모의 사용자·강의·신청·기간 지문은 라운드 전후 및 최종 종료 후 동일합니다. 데모 DB/볼륨을 초기화·삭제하지 않았습니다.

## 통계 정의

평균/중앙값/편차는 실행 단위로 계산했습니다. 편차는 `n-1`을 분모로 하는 **표본 표준편차**이며 n=1은 N/A입니다. n=2에서는 평균과 중앙값이 같아지는 것이 정의상 정상입니다. per-run p95/p99의 평균은 모든 HTTP 표본을 합친 백분위가 아닙니다.

모든 실행을 포함하여 목표 미달·중단을 숨기지 않았습니다. CPU/메모리 통계는 각 실행의 **샘플 peak**를 실행 간 집계한 값이며 시간 평균 CPU 사용률이나 절대 peak가 아닙니다. 오류율은 관측된 완료 응답의 5xx/네트워크 오류와 정상 FULL/DUPLICATE를 구분하고, 응답 미완료 요청은 별도 기록합니다.

## 0.5 CPU 저하: 일회성인가?

| half/A-100 | 실제 시작 / 완료 | 드롭 | 응답 미완료 | p95 / p99 ms | backend throttle 누적 관측 sec |
| --- | --- | --- | --- | --- | --- |
| 원래 | 319 / 119 | 55 | 200 | 2,072.86 / 2,572.92 | 62.13 |
| 추가 round 1 | 351 / 167 | 14 | 184 | 2,384.08 / 2,542.67 | 21.47 |
| 추가 round 2 | 322 / 122 | 60 | 200 | 2,301.00 / 2,657.75 | 79.64 |

**같은 fresh-backend/짧은 warm-up 조건에서 3/3회 보호 중단이 재현됐으므로, 이전 한 번의 우연한 환경 이상으로 보기 어렵습니다.** CPU quota 아래의 기동/JIT·스케줄·연결 획득 압박이 반복되는 제한 요인이라는 평가입니다.

- 추가 두 실행 모두 server 5xx와 관측된 network failure는 0, OOM도 0입니다. heap peak 약 41/44MiB, backend cgroup 약 192/197MiB로 1GiB 고갈 근거는 없습니다.
- 두 번째 추가 실행에서는 pool active/pending peak **11/3**을 관측했습니다. 누적 CPU throttling과 긴 응답, 획득 대기가 함께 나타났습니다. cgroup v1의 throttled time을 wall time이나 CPU 사용률로 환산하지 않았습니다.
- 추가 두 실행의 응답 수/목표 6초 기준 완료율은 27.83/s, 20.33/s입니다. 조기 중단/응답 누락이 있으므로 이를 안정적인 지속 처리량으로 해석하지 않습니다. 완료 응답의 지연 분포는 미완료된 가장 느린 요청을 포함하지 않아 오른쪽 tail이 잘린 관측입니다.
- 이번 추가 보호 중단의 총 드롭은 **74**, 응답 미완료 **384**입니다. 기존까지 합하면 각각 **129 / 584**입니다. 관측 5xx율 0%를 '모든 요청 성공'으로 바꾸지 않았습니다.
- 저부하 A-10/B-5/D-100은 같은 0.5 CPU에서 다시 정상적인 업무 처리·정합성을 유지했습니다. 따라서 애플리케이션의 일반적인 기능 장애나 모든 부하에서의 불능을 의미하지 않습니다.
- 이 결과는 **cold-ish 설정의 재현성**이며 충분히 워밍된 0.5 CPU의 steady-state 최대 용량을 확정하는 실험이 아닙니다. 별도의 긴 warm-up 조건을 이번 비교에 끼워 넣지 않았습니다.

## 목표 요청률 미달: 어디서 반복되는가?

시간창 미달은 이전 본 실험 19/82회(정상 종료 LIMITED 18회와 보호 중단 1회)에서 추가 11/56회(그중 보호 중단 2회)로 다시 관측됐습니다. 정상 종료한 추가 구성 중 LIMITED는 9회입니다. 이미지를 바꾸거나 기능을 수정하지 않은 상태에서 현상이 반복됐습니다.

- C4는 이전 2/3회, 추가 1/2회에서 목표 시간창을 놓쳤습니다. 추가 미달 실행은 10초 내 666건 시작, 전체 1,000건 처리 후 약 74.96 HTTP/s였습니다.
- 이 실행의 시작 사이 최대 공백은 **약 2,715.92ms**, 정상 추가 C4는 약 **11.45ms**였습니다. 반면 추가 p95는 3.47/4.01ms로 여전히 작았습니다.
- 추가 A-50/A-200/D-500의 미달 실행에도 약 **2.70~2.74초**의 요청 시작 공백이 잡혔습니다. 낮은 부하에서도 발생하고 높은 부하에서 정상인 실행도 있어 단순한 서버 최대 RPS 초과로 설명하기 어렵습니다.
- C3는 추가 두 번 모두 시간창 기준 LIMITED였습니다. 실제 시작 수가 **1,000/939**, 1초 내 시작이 **932/938**입니다. dropped_iterations=0이어도 목표 1,000명/1초를 입증하지 못할 수 있음을 다시 확인했습니다.
- C2 첫 추가 실행은 1,000건 중 999건이 시간창 안에 들어왔습니다. 이처럼 경계의 1건과 수 초의 큰 공백을 같은 정도의 과부하로 해석하지 않습니다. 엄격한 목표 미달 표시는 유지하되 실제 분포/정도를 함께 봅니다.

평가: **일회성으로 사라진 현상이 아니라 반복되는 간헐적 타이밍 제약**입니다. 다만 현재 도구의 상대 실행 시간과 timestamp만으로 실제 발생기 stall, WSL/호스트 스케줄링, 시간 계측 자체의 영향 중 하나를 확정할 수는 없습니다. 서버 처리 지연과 분리되는 발생기·공유 환경·하네스 시간 계층을 우선 진단하는 것이 타당합니다. 별도 발생기/독립 시계로 재검증하기 전 '앱의 지속적인 처리 용량 부족'으로 단정하지 않습니다.

## 지속적인 도메인 경합의 근거

추가 C2의 course-row-lock SQL 1,000회 누적 실행시간은 **2,044.69/2,227.02ms**, C3는 1,000/939회에 **2,771.67/2,594.03ms**였습니다. 추가 B-100에서는 600회에 **12.38/12.98ms**였습니다. Hikari acquire delta 평균도 B-100 약 **0.0085/0.0076ms**에 비해 C2 **2.36/3.30ms**, C3 **3.44/3.66ms**로 증가했습니다.

이전과 추가에서 같은 방향이 반복되므로 단일 인기 강의 행 잠금 및 연결 획득의 구조적 경합이라는 가설은 강화됩니다. 누적 SQL 실행시간은 여러 요청의 대기 합계를 포함하며 DB CPU나 wall time은 아닙니다. 1초 burst의 샘플 lock peak 0만으로 경합이 없다고 하지 않았습니다. 정원 초과·활성 중복·취소 카운트 이상은 없었습니다.

## CPU·메모리·DB와 오류율

실행별 CPU/memory/lock/pool 표는 결과 문서, 전체 원시 정규화 지표는 JSON에 있습니다. 각 구성의 이전/추가/합산 평균·중앙·SD와 range/CV도 JSON에 보존했습니다.

- 모든 추가 본 실험의 관측 5xx·network failure는 0이며 FULL/DUP와 분리했습니다. 미완료 384건은 성공/서버 오류/timeout으로 임의 분류하지 않았습니다.
- OOM 0, collector 오류 0. Docker VM 가용 메모리 최소 약 **11.94GiB**였습니다. 이번 관측으로 메모리 고갈을 주원인으로 지지할 수 없습니다.
- 같은 데이터 fingerprint와 설정을 확인했어도 JVM JIT·GC·물리 캐시·서버 기동 후 경과시간까지 동일한 것은 아닙니다. 이전에는 구성별 3회를 연속 실행했고 이번에는 전체 순서를 두 라운드로 반복했습니다.
- 원래 보호 중단 후 수동 확인 간격과 이번의 명시적 5초 회복 대기는 같지 않습니다. half/B-5 추가 p95는 평균 42.21ms, SD 23.75ms로 이전 평균 12.49ms보다 커졌지만, 실패 후 JIT/회복 이력·작은 표본이 섞이므로 새로운 회귀나 CPU만의 인과 효과로 단정하지 않습니다.
- Hikari rolling MAX에는 이전 실행이 남을 수 있고 PostgreSQL 누적 transaction/IO는 비동기 통계·collector/warm-up 영향을 받습니다. 실제 commit은 201/취소와 SQL 행 수로 판정했습니다.

## 미실행·검증·다음 판단

- 두 라운드의 기존 실제 28개 구성은 모두 시도했습니다. half/A-100은 각 1회만 재검증하고 드롭 보호 중단 후 같은 고부하를 연달아 강행하지 않았습니다.
- **NOT RUN:** 원래도 미실행이었던 E half의 높은 B-50/D-500, one/two의 A-100/B-50/D-500. 이번 목적은 기존 실제 부하의 반복 비교이며 새 고부하 확장과 혼합하지 않았습니다.
- **NOT RUN:** 30~60초 warm-up/긴 steady-state, 독립 발생기, CPU/heap 단일 변수 재설정, 앱 최적화, AWS. 새로운 조건은 비교군을 바꾸므로 이번에는 적용하지 않았습니다.
- 통계/원본 exporter 보호/격리 하네스 테스트 **9개 통과**. 앱 기능을 바꾸지 않아 Java/React 빌드 및 기능 테스트는 이번 반복 작업에서 재실행하지 않았습니다.
- 다음 순서는 독립적인 도착 시각 측정과 발생기 환경 안정화, cold/steady를 분리한 0.5 CPU 비교, 같은 burst에서 FULL 경로/row-lock 대기 비교입니다. 짧은 추가 n=2와 합산 n=5로 신뢰구간이나 클라우드 사양을 확정하지 않습니다.

## 재현

현재 로컬의 원래 image/fixture/벤치마크 volume을 유지한 상태에서 실행한 명령:

```sh
python3 load-tests/repeat_study.py --rounds 2 --high
python3 scripts/report-repeat.py
python3 -m unittest discover -s load-tests -p 'test_*.py'
```

기존 `.bench-results/repeat-study/manifest.json`이 있으면 실행기는 덮어쓰기와 우발적인 장시간 중복 실행을 거부합니다. 재차 별도 연구를 하려면 해당 manifest 디렉터리와 산출물을 먼저 별도 이름으로 보존해야 합니다. image·토큰·설정이 원본과 다르면 무시하고 진행하지 않고 중단합니다.

원본 2026-11-06 보고서와 JSON은 고정되어 있습니다. 추가 연구가 존재할 때 `scripts/report-bench.py`는 원본에 추가 실행을 섞지 않도록 거부하며, `scripts/report-repeat.py`만 새 비교 문서를 생성합니다. 토큰·환경 파일·대용량 시계열은 무시된 `.bench-results/`에 남기고 정제된 문서만 커밋합니다.
