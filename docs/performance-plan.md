# AWS 용량·비용 실험 계획 (후속 단계, Draft)

> **현재 Codex 작업 범위 아님.** 프론트엔드 검토/확정 → Spring Boot/PostgreSQL 구현 및 정합성 검증을 완료한 후 진행합니다. 아래 숫자/비용은 측정 결과가 아닙니다.

## 목표 질문
수강신청 오픈 직후 대규모 조회·신청 트래픽에서 AWS 인프라가 SLA/오류율/처리량 목표를 만족하려면 어느 정도 리소스가 필요한가? 시간당/이벤트당 비용은 얼마인가?

## 기준선 아키텍처
- ECS **Fargate** + ALB + RDS PostgreSQL; 단일 리전 AWS 환경
- Task별 vCPU/메모리와 desired count, RDS 사양을 명시하여 변경
- React 정적 배포는 S3/CloudFront 선택; 부하 시험은 주로 API 호출을 기준으로 수행
- Container Insights + CloudWatch, JVM/Micrometer 지표, HikariCP, RDS 메트릭 수집
- Terraform으로 재현 가능한 인프라, 예산·삭제 절차 마련
- EKS/EC2 비교는 필요성과 시간이 있을 때 별도 실험; EKS를 성능 향상의 전제조건으로 두지 않음
- Redis 대기열, 반응형 Auto Scaling은 **필수 아님**. 원인/요구가 명확할 때만 추가

## 독립 변수와 테스트 순서
1. 동일한 DB 시드·동일 이미지·동일 부하 시나리오에서 Fargate 최소 구성의 **기준선** 측정.
2. Task 메모리만 변경하고 JVM 힙·GC·OOM을 확인.
3. Task vCPU만 변경하고 처리량·지연을 확인(유효한 Fargate CPU/메모리 조합 준수).
4. Task 개수 1 → 2 → 4 등 변경; RDS 병목이 공유되는지 확인.
5. HikariCP/DB 크기 변경과 잠금 경쟁을 관찰.
6. 수강신청이 예측 가능한 이벤트이므로 **이벤트 시작 전 사전 증설**, 종료 후 축소. 준비된 Task가 정상 헬스체크를 통과했는지 확인.
7. 마지막에 성능·비용·안정성 요구에 근거해 최종 구성을 채택.

## k6 부하 시나리오
- **읽기 전용:** 강의 검색/목록, 가능한 경우 캐시 영향 검토
- **쓰기 중심:** 정원이 충분한 여러 강의에 신청해 진짜 쓰기 처리량 계측
- **핫스팟:** 인기 강의 마지막 자리를 여러 사용자가 경쟁; 정합성(성공 1건 등) 측정
- **혼합 트래픽:** 로그인 → 목록 조회 → 신청 → 신청 내역 조회
- 점진적 부하 상승과 일정한 도착률 유지, 반복 실험/냉·온 상태 구분
- k6 클라이언트가 병목인지 CPU/네트워크/응답 오류 확인
- 마감·중복 같은 **정상 비즈니스 결과를 장애 5xx와 구분**
