# Frontend Mock Prototype — Codex 구현 명세 (v1)

> **현재 구현의 유일한 기능 명세**입니다. 목적은 수강신청 사용자 흐름을 직접 경험하고 검토하는 것입니다. 실서버/DB/Redis/AWS는 연결하지 않습니다.

## 1. 기술·구조
- React + TypeScript + Vite. UI 컴포넌트 라이브러리는 자유롭게 선택하되 과도한 의존성은 피합니다.
- `frontend/`에 프론트엔드만 구현. 단일 페이지 앱; 로컬 실행 가능.
- 화면/컴포넌트, 도메인 상태, Mock 저장소(repository)/서비스를 구분해 이후 HTTP API로 교체하기 쉽게 만듭니다.
- 학생/강의/수강 내역 데이터는 **가상 데이터**만 사용. 비밀번호는 실제 계정의 보안 자격증명으로 취급하지 않으며 시연용임을 표시.
- 인프라 성능 측정이 목적이므로 고가의 시각 디자인이나 정교한 학사 업무 로직에 시간을 쓰지 않습니다.

## 2. 필수 화면
| 화면 | 필수 UI 요소 | 동작 |
| --- | --- | --- |
| 로그인·회원가입 | 이름(가입), 이메일, 비밀번호, 오류 메시지 | Mock 계정으로 가입/로그인/로그아웃 |
| 입장/오픈 대기 | '수강신청 시작 10:00' 안내, 시연용 오픈 전환, 입장 버튼 | 오픈 전 버튼 비활성; 데모에서 오픈 상태로 전환 후 입장 |
| 강의 목록 | 강의명, 코드, 교수, 정원, 현재 신청 인원, 신청 버튼, 검색 | 오픈 후 입장한 사용자에게만 표시 |
| 내 신청 내역 | 신청한 강의 목록, 취소 버튼, 빈 상태 | 신청/취소 즉시 반영 |
| 상태 피드백 | 성공, 정원 마감, 이미 신청, 취소 성공, 입력 오류 | 명확한 문구와 버튼 상태 |

별도의 관리자 UI, 대기열 진행 화면, 가짜 처리 지연/로딩 연출은 요구하지 않습니다.

## 3. 수강신청 규칙 (Mock UI)
1. 가상 학기 1개, 가상 강의 **20~30개**를 미리 준비. 강의 정원과 현재 신청 인원을 설정하되 빈 자리/마감 강의를 함께 제공.
2. 동일 학생이 동일 강의를 두 번 신청할 수 없습니다.
3. `enrolledCount < capacity`인 경우만 신청 가능; 성공 시 1 증가하고 내 내역에 추가.
4. 취소 시 내 내역에서 제거하고 해당 강의의 신청 인원을 1 감소. 중복 취소로 음수가 되면 안 됨.
5. **시연용 Mock이므로 단일 브라우저 내 일관성만 보장.** 여러 사용자·여러 기기 동시성은 백엔드 단계에서 보장.
6. 검색/필터는 비어 있는 결과와 마감 강의도 자연스럽게 보여줄 것.
7. 서로 다른 데모 계정으로 전환할 때 신청 내역이 사용자별로 섞이지 않도록 할 것.
8. 리프레시 후에도 데모를 이어갈 수 있도록 localStorage 등으로 상태 보존 가능; 테스트/리뷰를 위한 초기화 기능 제공.

## 4. 시연 시나리오 (인수 기준)
- [ ] Demo/Mock 표시가 보이며 실제 인증/DB 저장으로 오해되지 않는다.
- [ ] 회원가입 → 로그인 → 수강신청 오픈 대기 화면에 접근한다.
- [ ] 오픈 전에는 강의 목록에 접근하지 못하고, 시연용 조작으로 오픈 후 입장 가능하다.
- [ ] 입장 버튼 클릭 후 **대기열 없이** 강의 목록으로 이동한다.
- [ ] 강의 20~30개가 표시되고 강의명 등으로 검색할 수 있다.
- [ ] 자리 있는 강의 신청 시 성공 상태와 수강 내역·현재 인원 변화가 즉시 보인다.
- [ ] 같은 계정의 같은 강의 중복 신청이 방지된다.
- [ ] 마감 강의 신청은 실패하거나 비활성화되어 이유가 표시된다.
- [ ] 신청 취소하면 내 내역에서 삭제되고 정원 잔여 수가 회복된다.
- [ ] 로그아웃/다른 데모 계정 전환 시 사용자별 신청 내역을 구분한다.
- [ ] 새로고침/데모 초기화 동작이 예측 가능하며 문서에 설명되어 있다.
- [ ] `frontend/README.md`에 설치, 실행, 빌드 및 시연 경로가 적혀 있다.

## 5. 후속 단계와 분리
프론트엔드 검토/확정 뒤에야 Spring Boot API, PostgreSQL 트랜잭션과 실사용 인증을 구현합니다. 현재 Mock 검증 결과를 **실제 서버 정합성, 보안성, 동시성 보장**으로 확대 해석하지 마세요. AWS 성능 테스트는 그다음 단계입니다.

## 6. 리뷰에서 결정할 것
실제 사용 흐름, 필요한 입력·메시지, 오픈/입장 경험, 정원 표현, 신청·취소 UX. 이것이 확정되기 전에는 백엔드 API 스키마를 확정하지 않습니다.
